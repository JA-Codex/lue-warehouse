## Story

As a business stakeholder, I want a written report presenting the five insights in plain language so that I can act on them without reading SQL or the dashboard.

## What was done

1. **Added `insights_report(f, path)`** to `etl/reports/build.py` — a PDF builder that follows the same `build()` / `p()` / `table()` pattern as `cleaning_report()` and `quality_report()`.  It reads no new database queries; it draws on the same `facts_mod.collect()` output for context (profile, seed, window) and embeds the five insights as static prose with the SQL-sourced numbers.
2. **Updated `main()` in `etl/reports/build.py`** — added `("LUE_Business_Insights_Report.pdf", insights_report)` to the report loop so the PDF is generated alongside the cleaning and quality reports.
3. **Added `--insights` flag** (optional) — running with `--insights` generates only the insights report; without it, all three reports are generated.  This matches the `Makefile` `insights-report` target added in this story.
4. **Added `insights-report` target to `Makefile`**: `$(PYTHON) etl/reports/build.py --insights`.
5. **Report structure** (five sections):
   - 1. Summary table: five insights, one row each (ID, title, query, finding, planted pattern).
   - 2–6. One section per insight: 2-sentence finding, supporting table of key values from the query, implication for management.
   - 7. Data notes: synthetic data caveat, profile and seed, window.

## Decisions

- The insights report reads no new DB queries beyond what `facts_mod.collect()` already fetches; the five insight values are embedded as constants derived from the analytical queries run in US-14.1 and stored in `docs/evidence/us-14.1/01_insights_shortlist.md`.  This keeps the report generator offline-safe and avoids duplicating the analytical SQL in Python.
- The `--insights` flag is added so CI can test the report builder without generating all three PDFs (the cleaning and quality reports need a loaded warehouse to be meaningful).
