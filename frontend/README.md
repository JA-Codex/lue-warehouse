# Owner portal

A web UI for a property owner over the LUE warehouse. Five pages: My Portfolio, Collections & Arrears, Occupancy &
Leasing, Maintenance, Recommended Actions. The reference design's valuation, telemetry and AI-confidence widgets, and the
operator screens (role gateway, pipeline monitor, settings), are left out because the warehouse has no such data.

Two modes, one page:

| | Snapshot (default) | Live |
|---|---|---|
| Command | `make frontend` | `make frontend-live` |
| Reads | `frontend/data.js`, built from the recorded run | the warehouse, as `lue_reader`, through `/api/data` |
| Needs | Python only | the loaded warehouse, `make db-deploy`, `.env` |
| Owners | the 40 highest by NOI | all owners, plus their monthly NOI |
| Badge in the page | Snapshot | Live, with the time of the last read |

## Live mode: set up

1. Warehouse loaded (`make rebuild PROFILE=full`, or your existing run).
2. `make db-deploy` applies `sql/50_reporting/02_owner_portal.sql` (15 `vw_portal_*` views in `lue_reporting`). Safe to re-run.
3. `.env` has `PGHOST`, `PGPORT`, `LUE_READER_USER`, `LUE_READER_PASSWORD` (the same as Power BI uses).
4. `make frontend-live`, open <http://127.0.0.1:8080>. The terminal says `reading the warehouse as lue_reader ...` and then
   `LUE owner portal (live)`. If it cannot read the warehouse it says why and stops.

How fresh is it? The page asks the server every 60 seconds and the server re-reads at most every 20 seconds
(`--cache N`). Thirteen views are the analytical queries over `lue_dw`, so they show new data as soon as a load commits.
The portfolio tiles come from the marts, which the pipeline refreshes in its last stage, so they update when a pipeline
run finishes. This is near-real-time, not streaming: the warehouse itself only changes when the pipeline runs.

The server is read-only (GET only), listens on 127.0.0.1, serves three paths, and connects with the read-only role.

## Test it

**1. Automatic, no database (a few seconds):**

    python scripts/test_frontend.py        # or: make frontend-test      -> RESULT: 27/27 checks passed

D = snapshot data agrees with the recorded dashboard values (Billed, Arrears, Maintenance Cost, Resolved Requests, SLA
Breaches, Cash Received, NOI = rent - maintenance - fee, units held). H = the page. L = live mode without a database:
the assembler, the server (cache, stale fallback, 503/404/405, only three paths served) and that the generated SQL file is
current. It also runs in `python scripts/run_ci.py gen-test` and `contract`.

**2. Live mode against your warehouse (the test that matters).**

1. `make frontend-live`. The badge reads **Live**.
2. Pick an owner and compare with `psql` as `lue_etl`: run Q12 in `sql/60_analytics/analytical.sql`. `rent_collected`,
   `maintenance_cost`, `management_fee` and `noi` must equal the My Portfolio tiles; `noi_rank` the rank.
3. The portfolio figures must equal the Power BI Executive Overview (collection rate, arrears, occupancy).
4. Query the views directly: `SELECT count(*) FROM lue_reporting.vw_portal_owner_holding;` as `lue_reader` returns rows,
   and `SELECT * FROM lue_etl_only_table` as `lue_reader` is refused (the role still cannot read `lue_dw`).
5. Watch it change: with the portal open, `make next-extract`, then `make pipeline`. When the run ends, the next refresh
   (within a minute) shows the new figures and a new "updated" time. Or call
   <http://127.0.0.1:8080/api/data?refresh=1> to force a read.
6. Stop PostgreSQL and wait a minute: the badge turns amber, "Live, last read failed", and the page keeps the last data.

**3. By eye** (snapshot or live): switch owner; every page changes. A building with a high arrears ratio is marked Critical
on My Portfolio and gets a "Push collections" card on Recommended Actions. Copy a card and paste it somewhere. Narrow the
window to phone width. Switch the operating system to dark mode.

## Files

| File | Job |
|---|---|
| `index.html` | the whole UI; reads `api/data` if it exists, else `data.js` |
| `serve.py` | local server; `--live`, `--port`, `--cache`, `--no-browser` |
| `live_data.py` | reads the views and the marts as `lue_reader` |
| `portal_data.py` | shapes either source into the page's JSON (one code path for both) |
| `build_data.py` | rebuilds `data.js` from `docs/evidence/` and `data/` (`make frontend-data`) |
| `../sql/50_reporting/02_owner_portal.sql` | generated by `make portal-sql` from `analytical.sql`; do not edit |
| `../scripts/export_portal_sql.py`, `../scripts/test_frontend.py` | generator and tests |

## Limits

- Per-owner figures are rent, maintenance, fee, NOI, units held and monthly NOI. Arrears, renewals, SLA and cost are for
  the whole building, not an owner's units (the warehouse does not split a building's arrears by owner), and the page says so.
- The recommendation rules (arrears at least 1.5 times the portfolio, renewals under 20%, SLA misses 5 points above, cost 1.5
  times) are thresholds chosen here; change them in `flags()` in `index.html`.
- Live mode was tested here against a PostgreSQL with your real table definitions and reporting layer but no rows, and with a
  stand-in server for the page. It has not yet run against a loaded warehouse; test 2 above is that run.
